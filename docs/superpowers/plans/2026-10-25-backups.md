# Backups to S3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ежедневный зашифрованный бэкап PostgreSQL в AWS S3 через restic с ротацией, ежемесячной проверкой восстановления, пингами healthchecks.io и инструментом отката бакета после атаки.

**Architecture:** Bash-скрипты в `ops/backup/` на хосте, запускаются systemd-таймерами от root. restic работает в контейнере `restic/restic:<pin>`, дамп идёт потоком `pg_dump | restic backup --stdin`. Все внешние команды (restic, pg_dump, psql, pg_restore) вызываются через переопределяемые переменные — так скрипты тестируются в Linux-контейнере против MinIO и Postgres без хоста. `undelete.py` (boto3) — отдельная утилита владельца, тестируется на moto.

**Tech Stack:** bash (POSIX-утилиты + `curl`, `jq`), restic (закреплённая версия), Docker / Compose, systemd, MinIO (тесты), Python 3.13 + boto3 + moto (undelete), shellcheck.

**Spec:** `docs/superpowers/specs/2026-10-25-backups-design.md`

## Global Constraints

- Регион `eu-central-1`; репозиторий `s3:s3.eu-central-1.amazonaws.com/<bucket>/aichat`.
- Секреты только в `/etc/aichat/restic.env` и `/etc/aichat/restic-password` (root:root, 600); пароль передаётся restic как файл (`RESTIC_PASSWORD_FILE`); ничего из секретов — в git, логи, `ps`, тело пинга.
- Никаких `set -x`; все скрипты `set -euo pipefail`.
- Дамп никогда не пишется на диск: `pg_dump -Fc` → stdin `restic backup --stdin --stdin-filename aichat.dump --tag aichat-db --host aichat`.
- Ротация: `forget --tag aichat-db --keep-daily 7 --keep-weekly 4 --keep-monthly 3 --prune`.
- Ночной бэкап никогда не делает `restic init`; отсутствие репозитория — ошибка.
- `restic unlock` (без опций) перед бэкапом; контейнер restic всегда с `--hostname aichat` и кэшем `/var/cache/aichat-restic`.
- `restic check` — по воскресеньям после бэкапа.
- Пинги healthchecks.io: `<url>/start` в начале, `<url>` при успехе, `<url>/fail` при ошибке с телом ≤ 1024 байт; `curl -fsS -m 10 --retry 3`; сбой пинга не меняет код выхода; если URL не задан — предупреждение в журнал и пропуск.
- Статус-файлы: `/var/lib/aichat-backup/status.json`, `/var/lib/aichat-backup/restore-test.json`.
- Restore-test: временная БД `restore_test`, удаляется всегда (trap); провал, если последний снапшот старше 48 часов.
- Таймеры: бэкап `*-*-* 03:30:00`, `RandomizedDelaySec=10min`, `Persistent=true`; restore-test `*-*-01 04:30:00`, `Persistent=true`.
- Образ restic: точная версия, вышедшая не позже чем за 2 недели до реализации (записать в `ops/backup/RESTIC_VERSION`).
- Тексты для владельца (инструкции, сообщения об ошибках) — на русском.

## Review Focus

1. **Секрет утёк в вывод** — пароль restic, ключ AWS или URL проверки не появляются ни в stdout/stderr скриптов, ни в status.json, ни в теле пинга. Тест: `test_no_secrets_in_output` (Task 2).
2. **Расшифрованный дамп на диске** — после бэкапа в `/tmp` и рабочих каталогах раннера нет файлов `*.dump`. Тест: `test_dump_never_touches_disk` (Task 2).
3. **Пустой снапшот при упавшем pg_dump** — pipefail срабатывает и снапшот с нулевым/обрезанным дампом не создаётся. Тест: `test_pg_dump_failure_no_snapshot` (Task 2).
4. **Временная БД остаётся после сбоя проверки** — `restore_test` удаляется и при ошибке pg_restore. Тест: `test_restore_db_dropped_on_failure` (Task 3).
5. **undelete с ключом сервера** — утилита отказывается работать, если у переданных учётных данных нет права `s3:ListBucketVersions` / версии недоступны, с понятным сообщением, а не частичным откатом. Тест: `test_undelete_refuses_without_versioning` (Task 4).

**Interfaces:**
- `iam-policy.json`: шаблон с плейсхолдером `BUCKET_NAME`; Allow и Deny ровно по спеке 5.3 (Allow: `s3:ListBucket`, `s3:GetBucketLocation`, `s3:ListBucketMultipartUploads` на `arn:aws:s3:::BUCKET_NAME`; `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`, `s3:AbortMultipartUpload`, `s3:ListMultipartUploadParts` на `arn:aws:s3:::BUCKET_NAME/*`. Deny: `s3:DeleteObjectVersion`, `s3:PutBucketVersioning`, `s3:PutLifecycleConfiguration`, `s3:PutBucketPolicy`, `s3:DeleteBucketPolicy`, `s3:PutBucketObjectLockConfiguration`, `s3:DeleteBucket` на оба ARN).
- `lifecycle.json`: три правила с пустым фильтром — `NoncurrentVersionExpiration.NoncurrentDays = 30`; отдельное `Expiration.ExpiredObjectDeleteMarker = true`; `AbortIncompleteMultipartUpload.DaysAfterInitiation = 7`.
- `undelete.py` — CLI: `python undelete.py --bucket B [--prefix aichat/] --as-of "2026-11-02T10:00:00Z" [--apply] [--profile P] [--region eu-central-1]`.
  - Функция `plan_restore(s3, bucket: str, prefix: str, as_of: datetime) -> list[Action]`, где `Action = (kind: "restore"|"delete"|"keep", key: str, version_id: str|None)`.
  - Для каждого ключа под `prefix` (через `list_object_versions` с пагинацией): целевая версия = последняя *версия объекта* (не delete marker) с `LastModified <= as_of`. Если её нет → `delete` (объект появился после момента). Если она уже текущая (`IsLatest`) → `keep`. Иначе → `restore` (copy_object из этой `VersionId` поверх ключа).
  - `apply_actions(s3, bucket, actions) -> None`; без `--apply` — только печать плана и сводки «восстановить N, удалить M, без изменений K».
  - Перед работой: `get_bucket_versioning` должен вернуть `Status == "Enabled"`, иначе выход с кодом 2 и текстом «Версионирование бакета не включено — откат невозможно». `AccessDenied` на `list_object_versions` → код 2, «Нет прав на чтение версий: запустите с учётной записью владельца, не ключом сервера».
