# Бэкапы базы в AWS S3 (этап 2, часть 1) — дизайн

Дата: 2026-10-25
Статус: согласован в чате, ожидает ревью документа
Основная спека проекта: `docs/superpowers/specs/2026-10-17-ai-chat-design.md` (раздел 10).

## 1. Зачем

Сайт работает на VPS (`aramistrio.online`, Docker Compose: `db`, `app`, `caddy` в `/opt/aichat`).
Сейчас есть только ночной `pg_dump` в `~/backups` на **том же** сервере и ручное копирование к себе.
Нужно, чтобы:

- при полной потере сервера базу можно было восстановить из копии вне сервера;
- при взломе сервера злоумышленник не мог незаметно уничтожить историю бэкапов;
- содержимое бэкапов не мог прочитать никто, у кого есть доступ только к бакету (утечка ключа S3, ошибка настроек
  AWS, сотрудник AWS). Оговорка: тот, кто получил root на сервере, и так видит живую базу и `.env`, поэтому
  шифрование бэкапов от него не защищает — и не должно (решение builder'а, см. раздел 4);
- всё работало без участия владельца, а он узнавал о сбоях (уведомления — в следующей части, Telegram).

Успех: каждую ночь в S3 появляется зашифрованный снапшот; раз в месяц сервер сам доказывает, что из последнего
снапшота база восстанавливается; есть пошаговая инструкция восстановления на новом сервере, проверенная хотя бы раз.

## 2. Цели, не-цели, анти-цели

**Цели**
- Ежедневный зашифрованный бэкап базы PostgreSQL в AWS S3 (`eu-central-1`, Франкфурт).
- Ротация: 7 дневных, 4 недельных, 3 месячных снапшота, удаление старого — автоматически на сервере.
- Защита истории от взломанного сервера через версионирование бакета (30 дней на восстановление удалённого).
- Ежемесячная автоматическая проверка восстановления.
- Инструкции: настройка AWS (точные права), установка на сервер, восстановление.

**Не-цели**
- Бэкап сертификатов Caddy (перевыпускаются сами), `.env` (хранится в менеджере паролей владельца),
  файлов пользователей (приложение их не хранит).
- Telegram-бот — следующая часть этапа 2 (здесь только задел: файл статуса; внешний сигнал о сбоях даёт
  healthchecks.io).
- Point-in-time recovery / WAL-архив — для 10 человек достаточно суточной точности.

**Анти-цели (провал, даже если «работает»)**
- Расшифрованный дамп лежит на диске сервера во время отправки (во временных файлах тоже).
- Секреты (ключи AWS, пароль restic) попадают в git, в логи или в вывод `ps`.
- Ключ сервера может удалить версии объектов, отключить версионирование или поменять lifecycle/политику бакета.
- Сбой бэкапа проходит молча (exit 0 / нет записи в журнале).

## 3. Решения, принятые с владельцем

| Вопрос | Решение |
|---|---|
| Хранилище | AWS S3, регион `eu-central-1`, отдельный бакет только под бэкапы |
| Шифрование | restic (шифрует на клиенте); пароль репозитория — на сервере в файле root-only + копия у владельца в менеджере паролей |
| Расписание и ротация | каждую ночь 03:30 (время сервера); `forget --keep-daily 7 --keep-weekly 4 --keep-monthly 3 --prune` |
| Кто чистит старое | сервер, автоматически; защита — версионирование бакета + запрет ключу сервера удалять версии; некактуальные версии живут 30 дней |
| Проверка | раз в месяц — автоматическое восстановление во временную БД |
| Сигнал «бэкап жив» | healthchecks.io: после каждого запуска сервер пингует проверку; нет пинга дольше суток — сервис сам пишет владельцу (почта, позже Telegram). Ловит и полную смерть сервера |
| Действия владельца | создать бакет и IAM-пользователя по инструкции, один раз положить ключи на сервер |

## 4. Решения builder'а (приняты мной, владелец может оспорить)

- restic запускается в официальном контейнере `restic/restic` с **закреплённой точной версией**
  (последний стабильный релиз, вышедший не позднее чем за 2 недели до реализации), а не ставится пакетом на хост.
- Запуск — systemd-таймеры на хосте (от root), не из приложения и не cron.
- Дамп идёт потоком: `docker compose exec -T db pg_dump -Fc` → `restic backup --stdin --stdin-filename aichat.dump`,
  без промежуточного файла.
- Цель «бэкап не прочитать» сформулирована против доступа к бакету, а не против root на сервере: шифрование
  с открытым ключом (age/GPG) ничего не добавит, пока на том же сервере лежит живая база.
- `restic init` — только вручную, один раз при установке. Ночной скрипт репозиторий никогда не создаёт:
  если репозитория «нет», это ошибка (возможная атака — спрятанный `config`), а не повод для init.
- У restic постоянный кэш на хосте (`/var/cache/aichat-restic`, монтируется в контейнер) и фиксированный
  `--hostname aichat` у контейнера — для скорости и корректной работы lock'ов.
- Восстановление бакета после подмены/удаления — скрипт `ops/backup/aws/undelete.py` (boto3), запускается
  владельцем со своими правами AWS (не ключом сервера): возвращает состояние бакета на заданный момент времени
  (снимает delete markers, восстанавливает предыдущие версии). Проверяется против MinIO с версионированием.
- Существующий пользовательский cron `~/aichat-backup.sh` (локальная копия в `~/backups`) остаётся как есть.
- Уведомления: журнал systemd, JSON-файл статуса для будущего Telegram-бота и пинги healthchecks.io.

## 5. Как это устроено

### 5.1 Файлы в репозитории

```
ops/backup/
  backup.sh               ночной бэкап: pg_dump | restic backup, затем forget --prune, статус
  restore-test.sh         ежемесячная проверка восстановления во временную БД
  restic.sh               обёртка: docker run restic/restic:<версия> с env-файлом и паролем (общая для скриптов)
  restic.env.example      шаблон /etc/aichat/restic.env (без секретов)
  systemd/aichat-backup.service, aichat-backup.timer
  systemd/aichat-restore-test.service, aichat-restore-test.timer
  aws/iam-policy.json     права IAM-пользователя сервера
  aws/lifecycle.json      lifecycle бакета
  aws/undelete.py         возврат бакета на момент времени (для владельца, его права AWS)
docs/backups.md           настройка AWS, установка на сервер, восстановление (рус.)
```

`docs/deploy.md` раздел 8 — ссылка на `docs/backups.md`, локальный бэкап описан как дополнительный.

### 5.2 Секреты на сервере

- `/etc/aichat/restic.env` (root:root, 600): `RESTIC_REPOSITORY=s3:s3.eu-central-1.amazonaws.com/<bucket>/aichat`,
  `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION=eu-central-1`.
- `/etc/aichat/restic-password` (root:root, 600) — пароль репозитория (генерируется при установке,
  длинный случайный), передаётся в контейнер как файл (`RESTIC_PASSWORD_FILE`), не через переменную окружения
  командной строки.
- В том же `restic.env` — URL проверок healthchecks.io: `HC_BACKUP_URL`, `HC_RESTORE_URL` (не обязательны:
  если не заданы, пинги пропускаются с предупреждением в журнале). URL проверки — тоже секрет (по нему можно
  слать ложные «всё хорошо»), в git не попадает.
- Ничего из этого не логируется; скрипты не включают `set -x`.

### 5.3 Бакет и права (настраивает владелец по `docs/backups.md`)

- Бакет в `eu-central-1`: Block Public Access — всё включено; шифрование по умолчанию SSE-S3;
  **Versioning: Enabled**; Object Ownership — bucket owner enforced.
- Lifecycle (`aws/lifecycle.json`): некактуальные версии удаляются через 30 дней; удаляются «осиротевшие»
  delete markers (`ExpiredObjectDeleteMarker` — отдельным правилом, не вместе с `Days`); незавершённые
  multipart-загрузки — через 7 дней.
- IAM-пользователь сервера (только программный доступ, без консоли), политика `aws/iam-policy.json`:
  - разрешено: `s3:ListBucket`, `s3:GetBucketLocation`, `s3:ListBucketMultipartUploads` на бакет;
    `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`, `s3:AbortMultipartUpload`, `s3:ListMultipartUploadParts`
    на `bucket/*` (restic нужны удаления для lock-файлов и prune; `DeleteObject` в версионированном бакете
    создаёт лишь delete marker);
  - явно запрещено (Deny): `s3:DeleteObjectVersion`, `s3:PutBucketVersioning`, `s3:PutLifecycleConfiguration`,
    `s3:PutBucketPolicy`, `s3:DeleteBucketPolicy`, `s3:PutBucketObjectLockConfiguration`, `s3:DeleteBucket`.
- Ключи доступа владелец кладёт в `/etc/aichat/restic.env`. Права владельца в AWS (root/admin) на сервер не попадают.

### 5.4 Ночной бэкап (`backup.sh`, таймер 03:30, `Persistent=true`, случайная задержка до 10 мин)

1. `restic cat config` — репозиторий должен существовать; «не найден» и сетевая ошибка различаются в тексте
   ошибки; в обоих случаях — выход с ошибкой (init не делается).
2. `restic unlock` (снимает только устаревшие lock'и), затем
   `docker compose --project-directory /opt/aichat exec -T db pg_dump -U aichat -Fc aichat` → stdin `restic backup --stdin --stdin-filename aichat.dump --tag aichat-db --host aichat`.
   Ошибка `pg_dump` должна валить весь запуск (pipefail), а не давать пустой снапшот.
3. `restic forget --tag aichat-db --keep-daily 7 --keep-weekly 4 --keep-monthly 3 --prune`.
4. По воскресеньям — `restic check` (структура репозитория, без чтения всех данных).
5. Пинг healthchecks.io: `<url>/start` в начале; в конце — `<url>` при успехе или `<url>/fail` при ошибке,
   с телом — коротким текстом ошибки без секретов (≤ 1 КБ). Таймаут пинга 10 с, 3 попытки; сбой пинга
   не валит бэкап, но пишется в журнал. Туда уходит только статус, никаких данных базы.
6. Записать `/var/lib/aichat-backup/status.json`: время, результат (`ok`/`error`), id снапшота, размер,
   длительность, текст ошибки (без секретов). Ненулевой код выхода при любой ошибке.

### 5.5 Ежемесячная проверка (`restore-test.sh`, таймер 1-го числа, 04:30)

1. `restic dump latest aichat.dump` (по тегу) → `pg_restore` во временную базу `restore_test` в контейнере `db`
   (создать → восстановить → проверить → удалить; удаление — даже при ошибке, через trap).
2. Проверка: восстановление без ошибок; в `users` ≥ 1 строки; таблица `alembic_version` присутствует и не пуста;
   **последний снапшот не старше 48 часов** (иначе — сбой: бэкапы перестали создаваться).
3. Результат — в журнал, в `/var/lib/aichat-backup/restore-test.json` и пингом `HC_RESTORE_URL`
   (так же, как в 5.4); ненулевой код при сбое.

### 5.6 healthchecks.io (настраивает владелец по `docs/backups.md`)

- Бесплатный аккаунт, две проверки:
  - `aichat-backup`: тип Cron, расписание `30 3 * * *`, часовой пояс сервера, grace 3 часа;
  - `aichat-restore-test`: тип Cron, `30 4 1 * *`, grace 1 день.
- Уведомления — на почту владельца (Telegram-интеграцию healthchecks.io можно включить позже).

### 5.7 Восстановление (runbook в `docs/backups.md`)

- **На том же сервере** (испорчены данные): остановить `app`, `restic dump <снапшот> aichat.dump | pg_restore --clean --if-exists`, запустить `app`.
- **На новом сервере**: шаги 1–6 из `docs/deploy.md`, но перед созданием админа — положить `restic.env` и пароль,
  восстановить базу из `latest`, затем `docker compose up -d`.
- **После взлома / удаления снапшотов**: сначала отозвать ключ сервера в IAM; затем со своего компьютера
  `ops/backup/aws/undelete.py --bucket … --as-of <время до атаки>` (в пределах 30 дней), затем `restic check`
  и восстановление; новый ключ сервера — после переустановки сервера.
- Выбор снапшота: `restic snapshots`.

## 6. Ошибки и граничные случаи

- Нет сети / S3 недоступен — ошибка, ненулевой код, статус `error`; следующей ночью — обычная попытка
  (`Persistent=true` догоняет пропущенный запуск после простоя).
- Залипший lock от прерванного запуска — обычный `restic unlock` перед бэкапом (restic сам снимает только
  устаревшие lock'и; фиксированный `--hostname` позволяет ему проверять PID).
- `db` не запущен — ошибка с понятным текстом, без снапшота.
- Повторный запуск одновременно (ручной + таймер) — systemd не запустит второй экземпляр того же юнита;
  restic-lock защищает репозиторий.

## 7. Проверка реализации

- Пинги проверяются против локального фейкового HTTP-сервера (записывает запросы): `/start` + успех,
  `/start` + `/fail` с текстом ошибки, недоступный сервер пингов не валит бэкап.

- `shellcheck` для всех скриптов — без замечаний.
- Локальный прогон end-to-end против MinIO в Docker (S3-совместимый, с версионированием): init → backup →
  снапшот виден → forget → restore-test проходит (в т.ч. `restic dump latest aichat.dump` находит файл,
  записанный через `--stdin-filename`); искусственная ошибка `pg_dump` → ненулевой код, нового снапшота нет;
  спрятанный `config` → backup падает без init; удаление объектов → `undelete.py` возвращает бакет, `restic check` ок;
  снапшот старше 48 ч → restore-test падает.
- Проверка прав IAM — на реальном AWS при установке, по чек-листу в `docs/backups.md`
  (ключ сервера может `restic backup`; `aws s3api delete-object-version …` с этим ключом → AccessDenied).
- Первую установку на сервер и первое восстановление владелец делает по `docs/backups.md`.
